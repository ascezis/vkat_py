# вкат.py — архитектура и ТЗ

Документ фиксирует суть проекта, границы MVP и техническое решение — по итогам обсуждения.
Дизайн (палитра, типографика, состояния) — в отдельном файле `design-system.md`, здесь не дублируется.

## 1. Суть проекта

Ученик приходит в группу по Python с опозданием (пропустил несколько занятий) и не понимает
происходящего. Инструмент — standalone-тренажёр, который за одно-два самостоятельных занятия
закрывает базовый разрыв: ученик проходит короткие задания с реальной проверкой кода и
подтягивается до уровня группы, не отвлекая преподавателя и не тормозя остальных.

**Не образовательная платформа, не CMS, не сервис школы.** Личная инициатива автора,
standalone-инструмент вне экосистемы школы.

## 2. Аудитория и сценарий использования

- Дети и взрослые в одном треке — без деления на «детскую» и «взрослую» версии контента.
  Тон нейтрально-простой, примеры через бытовые/игровые ситуации.
- Распространение — вручную: ссылка или флешка с папкой. Не привязано к CRM/личному кабинету школы.
- Заход разовый или повторный (например, вернуться и повторить тему) — прогресс хранится
  локально на устройстве ученика.

## 3. Границы MVP (сознательно вне скоупа)

**Входит:** Python до классов —
1. Переменные, типы, ввод/вывод
2. Условия (if/elif/else)
3. Циклы (for, while) — усиленный блок
4. Функции (объявление, аргументы, return) — усиленный блок
5. Списки и словари (база)
6. Строки (база)

**Не входит:** классы, рекурсия, сложное наследование, диагностический тест на входе
(идея обсуждалась, отложена — см. раздел 8), два отдельных тона подачи для детей/взрослых,
серверная часть, аккаунты/логин, синхронизация между устройствами, интеграция с
платформой/CRM школы, открытая документация по устройству инструмента.

Объём: ~20–30 заданий на 6 тем — рассчитано на одно-два занятия.

## 4. Технический стек

**HTML + CSS + vanilla JS, без сборки, без фреймворков.**

Причины (см. также обсуждение в переписке):
- React и Tailwind в нормальном режиме требуют шаг сборки и/или сеть — конфликтует с
  требованием «скинул на флешку — открыл — работает».
- Electron отпадает: тяжёлый, требует отдельной сборки под Windows/macOS, иногда упирается
  в права администратора на учебных/родительских компьютерах.
- Объём логики (20–30 заданий, линейная навигация) не оправдывает веса фреймворка.

**Python-движок: Pyodide** (CPython, скомпилированный в WebAssembly) — выполняется прямо
в браузере, без сервера и без интернета после первой локальной сборки пакета. Даёт честное
выполнение кода ученика, а не имитацию проверки через регулярки.

### Offline-требование
Всё, что обычно тянется из сети (шрифты, Pyodide-рантайм), должно лежать локально в папке
проекта на флешке. Открытие — через `index.html` в браузере, интернет не нужен ни на каком
этапе после того, как флешка собрана.

## 5. Механика проверки (три слоя)

Проверка кода ученика — не только «сошёлся вывод», а честная оценка по трём независимым слоям:

1. **Результат (логика).** Выполняем код ученика через Pyodide, сравниваем вывод/значения
   переменных с эталоном для конкретного задания.
2. **Структура.** Разбор кода в AST (модуль `ast` из стандартной библиотеки Python, доступен
   в Pyodide) — проверяем, что использована требуемая конструкция (например, реально цикл
   `for`/`while`, а не захардкоженный вывод; реально функция `def`, а не инлайн-код).
   AST, а не поиск подстроки в тексте — иначе легко обмануть проверку комментарием или строкой.
3. **Чистота кода.** Простой линтер (правила уровня PEP8: длина строки, отступы, осмысленность
   имён переменных) — без кастомных «умных» эвристик, готовый минимальный набор правил.

**Правило показа результата:** слои 1 и 2 определяют, засчитано ли задание (можно двигаться
дальше). Слой 3 **не блокирует прогресс** — отображается отдельным блоком «Как сделать лучше»
под результатом, если есть замечания. Так задание не превращается в стену для новичка на
первом занятии, но привычка к чистому коду всё равно закладывается.

## 6. Структура урока (экран)

Двухпанельный layout (см. `lesson-mockup.html`):
- Слева — объяснение темы + короткий пример + формулировка задания.
- Справа — редактор кода, кнопка проверки, зона результата (засчитано/не засчитано +
  вывод консоли + опциональный блок «как сделать лучше»).
- Сверху — тонкая линия общего прогресса по курсу.
- Снизу — точки прогресса внутри текущей темы (шаг N из M).

Стартовый экран (см. `start-mockup.html`) — воздушный, одна колонка, три цифры
(тем / заданий / ориентировочное время), одна кнопка «Начать». Контраст с плотным
экраном урока — намеренный, чтобы вход не пугал объёмом.

## 7. Контент и структура файлов

Контент редактирует автор самостоятельно (не CMS, не админка — файлы). Предлагаемая структура:

```
/vkat-py/
  index.html              — точка входа
  /assets/
    /fonts/               — IBM Plex Sans/Mono, .woff2, локально
    /pyodide/             — рантайм Pyodide, локально
  /app/
    app.js                — навигация, состояние, локальное сохранение прогресса
    checker.js            — три слоя проверки: результат / AST / линтер
    styles.css            — общие стили по design-system.md
  /content/
    01-variables.json
    02-conditions.json
    03-loops.json
    04-functions.json
    05-lists-dicts.json
    06-strings.json
```

Формат одного файла темы — JSON (или Markdown с фронт-маттером, если удобнее автору для
правки текста руками): список заданий, для каждого — условие, эталонный код/ожидаемый вывод,
требуемые AST-конструкции, текст подсказки.

Прогресс ученика — `localStorage` браузера, привязан к конкретному устройству, без синхронизации.

## 8. Открытые вопросы (не финализированы)

- **Диагностический вход** (пропускать вперёд тех, кто щёлкает базовые темы без ошибок) —
  идея одобрена в переписке как красивая, но явно отложена за границы MVP. Если решим
  делать — это отдельная итерация поверх линейной версии, не блокирует старт разработки.
- **Единый тон vs переключатель тона** (для детей / взрослых) — решено делать один тон,
  переключатель эмодзи/подбадриваний как опциональное дополнение, не для MVP.

## 9. Защита авторства

- Личный бренд (имя/название проекта, не название школы) — в интерфейсе (футер/шапка) и в
  метаданных файлов (title, favicon, комментарии в коде).
- Исходники не публикуются в открытом виде; для сборки — минификация/обфускация JS.
  Это не защита от профи, но отсекает случайное присвоение "препод скопировал папку".
- Тема разграничения доступа к исходному коду — за пределами этого документа, решается
  отдельно на уровне процесса передачи файлов.

## 10. Связанные документы

- `design-system.md` — палитра, типографика, состояния интерфейса, правила «что не делать».
- `lesson-mockup.html` — образец экрана урока (тема «циклы»).
- `start-mockup.html` — образец стартового экрана.
