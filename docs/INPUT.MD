# Спецификация: ввод данных (`input()`) — «Stdin-программа»

> **Статус:** Запланировано (не реализовано). Зафиксировано как проектное решение, чтобы curriculum не остался без `input()`.
> **Автор решения:** обсуждение 2026-11-16 (см. также `docs/ROADMAP.md` v3.x и `FEATURES/CONNECT-PROTOCOL.md`).
> **Закон Zero-Build / Offline-First действует и здесь.**

---

## 1. Проблема

Браузер не имеет терминала: у Pyodide нет stdin, `input()` в рантайме падает с сырой ошибкой среды.
Весь текущий курс построен «бесstdin'ово» (данные — через параметры функций и `tests[]`),
поэтому выпускники не знают `input()` — базовую конструкцию настоящего Python.

Сейчас (v2.4.1) `input` входит в `_SAFE_BUILTINS` и падает с непонятной ученику ошибкой.
Точка подключения будущего решения — та же функция.

---

## 2. Выбранное решение: «судейский ввод» (fed-stdin)

Как на Stepik / в олимпиадных judges: у задания появляется панель **«Ввод программы»**
(textarea). Ученик пишет настоящий `input()`; при запуске код получает строки из панели.
С точки зрения ученика это неотличимо от ввода в настоящем терминале.

Отвергнутые альтернативы:
* **Только predict** (теория + «предскажи вывод при вводе 5 и 3») — дёшево, но ученик ни разу не напишет `input()` сам.
* **Полный интерактив (REPL-консоль)** — программа приостанавливается, ученик печатает строку.
  Технически возможно через `Atomics.wait`/`Atomics.notify` на SharedArrayBuffer между воркером и
  главным потоком, но требует: SAB-канал, консольный UI, «усыпление» watchdog на время ожидания
  ввода. Это фича уровня v3.x, не блокер для curriculum.

## 3. Архитектура решения

### 3.1. Единый Python-бутстрап (`index.html`, `script#vkat-checker-python`)

В `_SAFE_BUILTINS` подменяем `input` на контролируемую заглушку:

```python
_VKAT_STDIN_LINES = []          # строки ввода текущего запуска

def _student_input(prompt=''):
    if _VKAT_STDIN_LINES:
        return _VKAT_STDIN_LINES.pop(0)
    raise EOFError('Программа просит больше ввода, чем задано в панели «Ввод»')

_SAFE_BUILTINS['input'] = _student_input
```

* `_exec_user_code` и `_run_task_tests` принимают параметр `stdin_lines`
  (список строк) и заполняют `_VKAT_STDIN_LINES` перед исполнением.
* `EOFError` → попадает в `_runtime_err` через существующий
  `except BaseException` — ученику показывается понятная ошибка.
* Отладочная подсказка в `FriendlyErrors`: `EOFError` + «ввод» →
  «Программа ждёт больше строк, чем написано в панели ввода».

### 3.2. Схема задачи (`TaskItem` в `docs/types.d.ts`)

```ts
interface TaskItem {
  // ...
  /** Строки, которые «придут» в программу через input() (панель «Ввод»). */
  stdin?: string;            // "5\n3" — поле панели, разделитель \n
}

interface TaskTest {
  // ...
  /** Per-test ввод для задач, где input() вызывается внутри функции. */
  stdin?: string;
}
```

* Панель предзаполняется из `task.stdin`; ученик может её править (экспериментировать).
* Для predict-заданий с `input()` — тот же механизм: код предсказания исполняется
  с `stdin` из задания (ученик не видит панель).

### 3.3. UI (редактор, `app/`)

* Под редактором появляется панель **«ввод»** — только когда у задания есть `stdin`.
* `CHECK`: панель передаётся в payload → воркер кладёт в `_VKAT_STDIN_LINES`.
* `RUN` (свободный запуск): тот же ввод из панели.
* Показ stdin ученику: как есть, без эха в выводе (паттерн judges; вывод — только stdout программы).

### 3.4. Харнесс и валидатор

* `dev/run_tests.py`: `check_solution` принимает `stdin` из задачи, кормит заглушку;
  predict-секции с `input()` тестируются тем же механизмом.
* Валидатор: проверка, что у задач с `stdin` непустое значение; контраст-тест
  «программа без input() не потребляет панель».

## 4. Куда встаёт в curriculum

* Новая тема **`l2_io_input`** («Ввод: input() и типы данных», ~10 шагов) — после
  Практикума (`feature/practicum`) или как первые задания темы `l2_text_data`:
  `input()` → `split()` → `int()` → «введи два числа, выведи сумму».
* Теория честно объясняет: «в настоящем Python input() ждёт строку в терминале;
  в тренажёре данные вводятся в панель — дальше всё как на настоящей машине».
* **Файлы — не проблема и не отдельная дыра:** в Pyodide есть виртуальная файловая
  система в памяти (MEMFS), `open()`/`with` работают офлайн. Тема `l1_files`
  из `AI-PROMPTS/THEME-MAP.MD` реализуема той же схемой «данные задаются в задании».

## 5. Этапы внедрения

| Фаза | Объём | Оценка |
|---|---|---|
| 0. Дружелюбная заглушка | `_student_input` с понятной ошибкой + `FriendlyErrors` + регресс | ~30 мин |
| 1. Fed-stdin в чекере | `stdin_lines` в `_exec_user_code`/`_run_task_tests` + схема + пердача в payload | ~2 ч |
| 2. UI-панель ввода | рендер панели, передача в CHECK/RUN, подсветка «задание использует ввод» | ~2–3 ч |
| 3. Тема `l2_io_input` | ~10 шагов + selftest + харнесс | ~1 сессия |
| 4. (v3.x) REPL-консоль | SAB/Atomics, sleep watchdog | отдельный спринт |

## 6. Definition of Done (фазы 1–3)

- [ ] Задание с `stdin` показывает панель; `input()` читает строки по порядку.
- [ ] Исчерпание ввода → понятная ошибка (EOFError), а не сырая среда.
- [ ] predict-задания с `input()` проверяются харнессом.
- [ ] Регресс в `run_tests.py`: input-задание проходит на эталоне и падает на неверном решении.
- [ ] Валидатор: у задач с `stdin` панель объявлена; без `stdin` панель не рендерится.
- [ ] Офлайн: работает на `file://` без сети (закон Zero-Build).
