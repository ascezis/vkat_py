# Руководство по разработке и сопровождению (CONTRIBUTING)

Добро пожаловать в разработку **вкат.py**! Этот документ описывает правила работы с ветками, соглашения по коммитам, чеклисты перед пушем и работу CI/CD-пайплайнов.

---

## 1. Философия и принципы проекта

- **Offline-first & No-build**: проект работает без npm-сборщиков (Webpack, Vite и т.д.). Чистый Vanilla JS, HTML и CSS. Всё, включая Pyodide (Wasm) и шрифты, лежит в репозитории и работает без интернета.
- **Строгий монохром**: эстетика терминала/редактора кода. Никаких случайных акцентных цветов, разделение состояний только через инверсию, вес линий и символы (см. [`docs/design-system.md`](file:///c:/Users/azis/Desktop/vkat_py-main/docs/design-system.md)).
- **Модульная архитектура**: ядро разбито на логические модули в каталоге `app/` (`app.js`, `profiles.js`, `renderers.js`, `checkers.js`), а темы лежат раздельно в `content/start/` и `content/core/`.
- **Зелёные тесты всегда**: перед любым пушем и слиянием обязательно прохождение автоматических валидаторов.

---

## 2. Работа с ветками (Branching Workflow)

1. **`main`** — стабильная ветка.
   - Любой коммит в `main` автоматически инициирует **деплой на GitHub Pages** и проверку на **выпуск нового релиза**.
   - Не пушьте сырой или непроверенный код напрямую в `main`.

2. **Создание веток под задачи**:
   - Новая фича: `feature/<краткое-описание>` (например, `feature/tuples-topic` или `feature/dark-mode-toggle`)
   - Исправление ошибки: `fix/<краткое-описание>` (например, `fix/safari-audio-context` или `fix/predict-input`)
   - Рефакторинг: `refactor/<краткое-описание>` (например, `refactor/decompose-app-js`)
   - Документация: `docs/<краткое-описание>` (например, `docs/contributing-guide`)

3. **Слияние через Pull Requests**:
   - Создавайте PR в ветку `main`.
   - В PR автоматически запускается пайплайн `CI` (прогон JS-валидации и Python-тестов).
   - Слияние разрешается только после успешного завершения всех проверок.

## 3. Соглашение о коммитах и авто-релизы

Для версионирования в проекте используется [Conventional Commits](https://www.conventionalcommits.org/).  
GitHub Actions анализирует заголовки и тела коммитов и автоматически вычисляет следующую семантическую версию (`vX.Y.Z`).

### Таблица типов коммитов и их влияние на версию

| Префикс | Влияние на версию | Пример | Будет ли создан релиз? |
|---|---|---|---|
| `fix:` | **Patch** (`+0.0.1`) | `fix: resolve Pyodide bootstrap syntax error` | **Да** |
| `perf:` | **Patch** (`+0.0.1`) | `perf: optimize AST traversal in code checker` | **Да** |
| `feat:` | **Minor** (`+0.1.0`) | `feat: add tuples topic to core course` | **Да** |
| `feat!:` или `BREAKING CHANGE:` | **Major** (`+1.0.0`) | `feat!: change storage schema for multiplayer mode` | **Да** |
| `refactor:` | *Нет бампа* | `refactor(app): decompose app.js into modules` | **Нет** (по умолчанию) |
| `docs:` | *Нет бампа* | `docs: add contributing and deployment guide` | **Нет** (по умолчанию) |
| `chore:` | *Нет бампа* | `chore: clean up obsolete test files` | **Нет** (по умолчанию) |
| `style:` | *Нет бампа* | `style: fix indentation in styles.css` | **Нет** (по умолчанию) |
| `test:` | *Нет бампа* | `test: add unit test for profile storage` | **Нет** (по умолчанию) |

> ⚠️ **Важно:** если в ветку `main` попадают только коммиты `refactor:`, `docs:` или `chore:`, сборщик релиза **пропустит создание тега и ZIP-архива** (в логах появится `Analysis of X commits complete: no release`).

### Как принудительно выпустить релиз при рефакторинге или обновлении доки

Если изменения значимы для пользователей и требуют релиза:
1. Добавьте в заголовок или тело коммита / PR явный тег: `#patch`, `#minor` или `#major`.
   ```bash
   git commit -m "refactor(app): decompose app.js #minor"
   ```
2. Или оформите PR с типом `feat:`:
   ```bash
   git commit -m "feat(arch): modular app structure and topics guide"
   ```
3. Или выставьте тег вручную локально:
   ```bash
   git tag v2.2.0
   git push origin v2.2.0
   ```

## 4. Локальный чек-лист перед коммитом и пушем

Перед созданием коммита обязательно выполните локальную проверку:

### 1. Валидация JS-кода и структуры контента
Запустите скрипт проверки целостности всех тем, синтаксиса и обязательных полей:
```bash
node dev/run_js_validation.js
```
Должен вернуть: `Все проверки пройдены! Ошибок нет.`

### 2. Тестирование решений задач на настоящем Python
Запустите тестовый раннер решений:
```bash
python dev/run_tests.py
```
Должен вернуть: `ИТОГ: X пройдено, 0 ошибок.`

### 3. Комплексный браузерный тест (Selftest)
1. Запустите сервер (через `run.bat` на Windows или `python3 -m http.server 8085`).
2. Откройте в браузере: `http://localhost:8085/dev/selftest.html`.
3. Убедитесь, что все тесты (включая проверку тем, рантайма и модулей) горят зелёным без исключений.

## 5. Пайплайны CI/CD (GitHub Actions)

В каталоге [`.github/workflows/`](file:///c:/Users/azis/Desktop/vkat_py-main/.github/workflows) настроены три независимых процесса:

### 1. `ci.yml` — Непрерывная интеграция
- **Триггер**: `push` в любые ветки, а также любые `pull_request` в `main`.
- **Что делает**:
  - Настраивает Node.js 20 и Python 3.12.
  - Запускает `node dev/run_js_validation.js`.
  - Запускает `python dev/run_tests.py`.
- **Цель**: защитить `main` от поломок синтаксиса или логики проверок.

### 2. `deploy.yml` — Публикация на GitHub Pages
- **Триггер**: `push` в `main` или ручной запуск (`workflow_dispatch`).
- **Что делает**:
  - Запускает валидацию (`run_js_validation.js` и `run_tests.py`).
  - При успехе загружает артефакты и деплоит сайт на GitHub Pages.
- **Публичный адрес**: [ascezis.github.io/vkat_py](https://ascezis.github.io/vkat_py/)

### 3. `release.yml` — Сборка версий и офлайн-пакетов
- **Триггер**: `push` в `main` или ручной запуск (`workflow_dispatch`).
- **Что делает**:
  - Проверяет тесты.
  - Анализирует коммиты через `mathieudutour/github-tag-action@v6.2`.
  - Если есть бамп версии:
    1. Создаёт и пушит тег (например, `v2.2.0`).
    2. Упаковывает автономный ZIP-архив `vkat_py-vX.Y.Z-standalone.zip` (исключая служебные файлы `.git`, `.github`, `dev/`, `AI-promts/` и временные патчи).
    3. Создаёт GitHub Release, крепит ZIP-архив и автоматически генерирует список изменений (changelog).

## 7. Часто задаваемые вопросы (FAQ)

### Почему после пуша в main не появился новый релиз?
Проверьте тип ваших последних коммитов. Если все коммиты имели тип `chore:`, `docs:` или `refactor:`, пайплайн `release.yml` не производит автоматический бамп версии. Чтобы выпустить релиз, укажите `#patch` / `#minor` в сообщении коммита или воспользуйтесь коммитом `feat:`.

### Почему в браузере при открытии index.html не работает код?
Браузеры блокируют загрузку WebAssembly (`pyodide.asm.wasm`) при открытии по протоколу `file://` из-за правил безопасности CORS. Открывайте проект только через локальный HTTP-сервер:
- На Windows: дважды кликните `run.bat`
- В терминале: `python -m http.server 8085` или `npx serve`

### Как добавить стороннюю JS-библиотеку?
В проект **не добавляются** зависимости из npm или внешних CDN. Если функционал критически необходим, код должен быть проверен на безопасность, оформлен в виде одного офлайн-файла и размещён локально внутри проекта.
