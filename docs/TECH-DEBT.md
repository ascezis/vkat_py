## 2. Подробный разбор проблем и решений

---

### P0. Зависание UI при зацикливании Python (Pyodide в основном потоке)

#### В чём проблема:
Сейчас [`app/checker.js`](file:///c:/Users/azis/Desktop/vkat_py-main/app/checker.js) исполняет Python-код через `pyodide.runPythonAsync()` прямо в контексте окна браузера.  
Если ученик допускает ошибку в цикле (например, забыл инкремент `i += 1` в `while`), главный поток браузера блокируется на 100%:
* Интерфейс замерзает, анимации останавливаются.
* Кнопки, переключатели тем и хоткеи перестают реагировать.
* Через 10–15 секунд браузер показывает модальное окно «Страница не отвечает». Ученик пугается и закрывает вкладку, теряя несохранённый черновик.

#### Архитектурное решение: Web Worker Sandbox («Антифриз»)
Вынести рантайм Pyodide в выделенный веб-воркер:
```
[ UI Thread (app.js) ]  <--- postMessage / onmessage --->  [ Web Worker (Pyodide) ]
         │                                                            │
  Таймаут 5 сек ───────────────── worker.terminate() ───────────────> Смерть зацикленного кода
```

#### План реализации:
1. Создать легковесный скрипт `app/checker-worker.js`.
2. В воркере инициализировать Pyodide и слушать сообщения: `{ code, tests, astRequirements }`.
3. В `app/checker.js` при отправке задачи запускать таймер на 5–7 секунд.
4. Если воркер не прислал ответ вовремя:
   * Вызвать `worker.terminate()`.
   * Мгновенно перезапустить новый экземпляр воркера в фоне.
   * Выдать ученику понятную Friendly-ошибку:  
     `«Программа выполнялась слишком долго (таймаут 5 сек). Возможно, в цикле while забыто изменение переменной?»`.

> ⚠️ **Ограничение Offline/`file://`:**  
> При прямом открытии страницы через `file:///` создание воркера `new Worker('app/checker-worker.js')` может блокироваться политикой безопасности некоторых браузеров.  
> **Обход:** Использовать Blob-воркер: `URL.createObjectURL(new Blob([workerCodeString], { type: 'application/javascript' }))`, либо прозрачный фолбэк на синхронный запуск, если воркер недоступен.

#### Статус: ✅ Решено в v2.4.0 (issue #2, «Антифриз»)

Реализовано в `app/checker-worker.js` + `PyodideWorkerBridge` (`app/checker.js`):
* Pyodide живёт в выделенном воркере; главный поток общается через `INIT/CHECK/RUN/PING`.
* Watchdog 7 с: зависший воркер терминируется, песочница пересоздаётся, ученик получает Friendly-ошибку про бесконечный цикл.
* `ensureReady()` ограничен JS-таймаутом 90 с (защита от воркера, зависшего до установки обработчиков).
* Краш воркера (OOM/wasm abort) **не** перезапускает код в главном потоке — возвращается `sandboxFailureResult`; перманентный fallback только после 3 крашей подряд.
* file://-режим прозрачно использует in-thread fallback (воркер блокируется CORS — ожидаемо), embedded-бинарники продолжают работать.

**Известные ограничения (принятый threat model — образовательный контекст):**
1. Песочница защищает от зависания, а не от злонамеренного кода: остаётся классический обход через `object.__subclasses__()`-walk (в рантайме Pyodide достижим `os`). Вред ограничен вкладкой самого ученика: воркер изолирован от DOM/localStorage.
2. Watchdog ограничивает только время, не память: `list(range(10**8))` может уронить вкладку (краш ловится, но окна OOM браузер не даёт обработать).
3. Loop-guard 1 млн итераций срабатывает раньше watchdog только на простых телах цикла.

### P1. Хрупкость модулей и глобальный скоуп (`window.*`)

#### В чём проблема:
Каждый модуль ядра экспортирует себя в глобальный объект: `window.VkatStorage`, `window.VkatApp`, `window.VkatCheckers`, `window.Glyphs`.  
Внизу [`index.html`](file:///c:/Users/azis/Desktop/vkat_py-main/index.html) прописан жесткий порядок из 25 тегов `<script>`.

* Зависимости между модулями **неявные** (например, `renderers.js` не объявляет, что ему нужен `code-hints.js` — он просто надеется, что тот уже лежит в `window`).
* Добавление новой темы требует правок сразу в двух местах: вставить `<script src="content/core/NN-topic.js">` в HTML и добавить ID в `content/stages.js`.

#### Архитектурное решение: Микро-контейнер зависимостей (Service Locator)
Без сборщиков и без Webpack создать ядро на 25 строк (`app/kernel.js`):

```javascript
(function (window) {
  'use strict';
  const registry = {};

  window.Vkat = {
    define(name, factory) {
      registry[name] = factory(registry);
    },
    get(name) {
      if (!registry[name]) {
        throw new Error(`[VkatKernel] Модуль '${name}' не зарегистрирован или загружен не в том порядке.`);
      }
      return registry[name];
    }
  };
})(typeof window !== 'undefined' ? window : global);
```

**Использование:**
```javascript
// app/app.js
window.Vkat.define('app', function(deps) {
  const storage = deps.storage;
  const checker = deps.checker;
  // Явные зависимости! Отсутствие конфликтов в window.
});
```

### P2. Отсутствие типизации контрактов (DX и масштабируемость)

#### В чём проблема:
В проекте более 210 учебных элементов с комплексной схемой (`astRequirements`, `tests`, 3-уровневые `hints`, типы `warmup`/`main`/`star`, `kind: "fix"`).  
Ошибки в названиях ключей (например, `explain` вместо `explanation` или `require_ifs` вместо `require_if`) сейчас ловятся **только** при запуске юнит-тестов `node dev/run_js_validation.js`. В редакторе кода разработчик не получает автодополнения и подсветки ошибок.

#### Архитектурное решение: JSDoc + `jsconfig.json` (TypeScript без компилятора)
Никаких `npm install typescript` и шагов сборки не требуется. Языковой сервер VS Code / Cursor / WebStorm умеет валидировать чистый JS «на лету».

1. Добавить в корень проектный конфиг [`jsconfig.json`](file:///c:/Users/azis/Desktop/vkat_py-main/jsconfig.json):
```json
{
  "compilerOptions": {
    "checkJs": true,
    "target": "ES2022",
    "moduleResolution": "classic"
  },
  "include": ["app/**/*", "content/**/*"]
}
```

2. Создать файл описания контрактов `docs/types.d.ts`:
```typescript
type ItemType = 'theory' | 'quiz' | 'predict' | 'code';
type CodeTier = 'warmup' | 'main' | 'star';

interface AstRequirements {
  require_def?: boolean;
  require_return?: boolean;
  require_for?: boolean;
  require_while?: boolean;
  require_loop?: boolean;
  require_if?: boolean;
  require_try?: boolean;
  require_raise?: boolean;
  forbid_calls?: string[];
  forbid_methods?: string[];
}

interface TaskItem {
  id: string;
  type: ItemType;
  title: string;
  tier?: CodeTier;
  kind?: 'fix';
  initialCode?: string;
  tests?: Array<{ call?: string; code?: string; returns?: any; stdout?: string }>;
  astRequirements?: AstRequirements;
  hints?: [string, string, string];
}
```

3. В начале любого `.js` файла добавить директиву:
```javascript
// @ts-check
```
* **Результат:** Ошибки подсвечиваются прямо во время набора текста, автодополнение работает по нажатию `Ctrl+Пробел`, а для браузера всё остаётся чистым нативным JS.

#### Статус: ✅ решено в v2.4.0–v2.4.1 (Sprint 3)

* `jsconfig.json` + `docs/types.d.ts`: строгие контракты контента (`TaskItem`, `TaskTest`, `AstRequirements`, `TheoryBlock`, `CourseTopic`, `CourseStage`), хранилища (`ProfileData`, `VkatStorageApi`) и чекера (`CodeCheckerApi`, `CheckResult`).
* **`checkJs: true` включён** (Sprint 3): стартовый прогон tsc дал 661 ошибку — ~630 из них были ошибки самого contracts-файла (слишком узкие типы, неверные имена полей `initialCode` vs `starterCode`, отсутствие `assignment`), а не кода. После вывода типов по реальной схеме и точечных JSDoc-аннотаций (без изменения рантайма) — **0 ошибок**.
* UI-модули (`VkatApp`, `VkatRenderers`, `VkatProfiles`, …) осознанно `Record<string, any>`: они смешивают состояние и методы; фиксация их контрактов — остаток в Sprint 3+.
* Валидатор (секция 20) следит, что контракты не потерялись.

### P1. Риск переполнения `localStorage` при многопользовательской работе

#### В чём проблема:
Модуль [`app/storage.js`](file:///c:/Users/azis/Desktop/vkat_py-main/app/storage.js) сохраняет черновики кода (`drafts`) с дебаунсом в `localStorage`.  
Лимит браузера на домен — **~5 МБ**.  
В школьном классе, где за одним компьютером за четверть успевают поработать 15–20 учеников, объем сохраненных черновиков по 75 задачам основного курса гарантированно приблизится к лимиту, что приведёт к фатальной ошибке `QuotaExceededError`.

#### Архитектурное решение:
1. **Гибридное хранилище:**
   * Метаданные профилей, PIN-коды и массив закрытых ID (`completed: [...]`) хранить в `localStorage` (занимает < 50 КБ на класс).
   * Массивные черновики кода (`codeDrafts`) сохранять в асинхронную базу данных **`IndexedDB`** (встроена во все современные браузеры, работает оффлайн, лимит — от сотен МБ до гигабайт).
2. **Сжатие черновиков:**
   * Хранить черновики **только** для тех задач, которые ещё не решены или отличаются от эталона.

#### Статус: обработка добавлена в v2.4.0, причина не устранена

* `QuotaExceededError` больше не молчит: раз в сессию пишется явное предупреждение в консоль и шлётся событие `vkat-storage-quota` для UI-слоя, приложение не падает. Ученик/учитель получает совет «экспортируйте и удалите старые профили».
* Перенос черновиков в `IndexedDB` (п. 1–2 решения) остаётся в backlog'е v2.5+.

### P3. Смешение данных и кода (Data as Code)

#### В чём проблема:
Весь контент (тексты уроков, вопросы тестов, код задач) хранится в виде исполняемых JavaScript-файлов:
`window.COURSE_TOPICS.push({ ... })`.  
Из-за этого:
* Все 9 тем и 211 элементов загружаются и парсятся в память браузера сразу при открытии страницы, даже если ученик проходит только первую тему «Переменные».
* Сложно отделить работу методиста/автора курса от кода самого приложения.

#### Архитектурное решение (Подготовка к v3.0):
Переход на концепцию **Манифеста курсов и ленивой загрузки** ([`FEATURES/ARCHITECTURE-IMPROVEMENTS.md`](file:///c:/Users/azis/Desktop/vkat_py-main/FEATURES/ARCHITECTURE-IMPROVEMENTS.md)):
* Подгружать скрипт темы через динамический `document.createElement('script')` только в момент, когда ученик выбирает её в дереве тем или завершает предыдущую.

### P3. Нагрузка Canvas-сетки на слабых ПК (`app/grid-warp.js`)

#### В чём проблема:
Модуль [`app/grid-warp.js`](file:///c:/Users/azis/Desktop/vkat_py-main/app/grid-warp.js) реализует математический расчёт деформации для тысяч точек в цикле `requestAnimationFrame`.  
Хотя засыпание при бездействии мыши (0% CPU) уже реализовано отлично, на старых школьных нетбуках со слабыми процессорами (Celeron / старые Intel HD Graphics) в момент движения мыши может происходить просадка частоты кадров.

#### Решение:
1. Проверять системную настройку экономии ресурсов:
   ```javascript
   const prefersReducedMotion = window.matchMedia('(prefers-reduced-motion: reduce)').matches;
   if (prefersReducedMotion) return null;
   ```
2. Динамически увеличивать `SPACING` (шаг сетки с 24px до 36px) на экранах с низким разрешением или слабой графикой, сокращая количество точек в 2 раза.
